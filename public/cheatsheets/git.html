Section 01

Basic Commands

Initialize repositories, inspect state, stage changes, and record commits with clear messages.

Tip

Configure identity once per machine: git config --global user.name "Your Name"; git config --global user.email "you@example.com".

git init

Create a new Git repository in the current directory or a specified path.

  • --bare: create a repo without working tree (for servers/remotes).
  • -b <name>: set initial branch name.
# Create repo with main as default branch
git init -b main

# Create a bare remote-style repo
git init --bare /srv/git/project.git

git clone

Copy an existing repository (local or remote) with history.

  • --branch/-b: checkout specific branch or tag.
  • --depth N: shallow clone with last N commits.
  • --recurse-submodules: initialize submodules.
  • --origin/-o: custom remote name (default origin).
# Shallow clone main branch
git clone --branch main --depth 5 https://github.com/org/app.git

# Clone with submodules and custom remote name
git clone --recurse-submodules -o upstream git@github.com:org/app.git

git status

Show working tree state: staged, unstaged, untracked files, and branch/HEAD info.

  • -s/--short: condensed output.
  • --branch: show branch and upstream (default with -s).
  • --ignored: include ignored files.
# Brief status with branch
git status -sb

# Show ignored files too
git status --ignored

git add

Stage file contents for the next commit.

  • -p/--patch: interactively stage hunks.
  • -A: stage all changes (tracked + untracked).
  • -u/--update: stage tracked file modifications/deletions.
  • .: stage current directory recursively.
# Stage interactively
git add -p src/app.py

# Stage everything (including deletions)
git add -A

git commit

Record staged changes with a message, creating a new snapshot.

  • -m: commit message inline.
  • -a: stage tracked file modifications before committing.
  • --amend: rewrite last commit (message or content).
  • --no-edit: amend without changing message.
  • --signoff/-s: add Signed-off-by trailer.
  • --gpg-sign/-S: sign commit with GPG key.
# Standard commit with message
git commit -m "Add user validation"

# Amend last commit after staging fixes
git commit --amend --no-edit

# Commit all tracked changes and sign off
git commit -am "Refactor auth middleware" -s

git log

View commit history with flexible formatting and filtering.

  • --oneline: compact one-line entries.
  • --graph: ASCII branch graph.
  • --decorate: show refs (branches/tags).
  • -n N: limit number of commits.
  • --since/--until: date filters.
  • --author/--grep: filter by author or message regex.
# Visual history graph
git log --oneline --graph --decorate -n 15

# Filter by author and date
git log --author="Alice" --since="2 weeks ago" --oneline

Section 02

Branching & Merging

Create, switch, merge, and rebase branches. Choose strategies that keep history clear.

Reminder

Merge keeps history branching; rebase rewrites commits atop a new base. Avoid rebasing shared branches.

git status

Identify conflicted paths after merge/rebase and see guidance for next steps.

  • git status: lists files with conflicts (both modified).
  • -sb: short output while keeping branch info.
# Show conflicted files and instructions
git status

# Delete merged branch
git branch -d feature/login

git diff

Inspect conflict markers and compare ours vs theirs.

  • git diff: view conflict blocks (<<<<<<<, =======, >>>>>>>).
  • --name-only --diff-filter=U: list only conflicted files.
  • --ours/--theirs: compare specific sides (with pathspecs).
# List conflicted files
git diff --name-only --diff-filter=U

# View markers inside a file
git diff -- config/routes.rb

git checkout

Legacy command to switch branches or restore files. Prefer git switch / git restore for clarity.

  • git checkout <branch>: switch branches.
  • git checkout -b: create and switch.
  • git checkout -- file: discard local file changes.
# Create and switch
git checkout -b docs/update-readme

# Discard changes to a file (cannot be undone)
git checkout -- README.md

git switch

Modern, branch-only switch command (safer than checkout).

# Jump back to previous branch
git switch -

# Create and switch to feature
git switch -c feature/payments

git merge

Combine histories, producing a merge commit (or fast-forward when possible).

  • --no-ff: create merge commit even if fast-forward.
  • --ff-only: fail unless fast-forward possible.
  • --squash: apply changes without creating merge commit.
  • --abort: stop merge and reset to pre-merge state.
# Merge feature into main
git checkout main
git merge feature/login --no-ff

# Abort merge after conflicts
git merge --abort

git rebase

Replay commits onto a new base to create a linear history. Avoid rebasing published branches.

  • git rebase <branch>: move current branch onto target.
  • -i/--interactive: reorder, edit, squash commits.
  • --onto A B: move range starting at B onto A.
  • --continue / --abort / --skip: control after conflicts.
# Rebase feature onto latest main
git switch feature/login
git fetch origin
git rebase origin/main

# Interactive cleanup before PR
git rebase -i HEAD~4  # squash, edit messages

Merge vs Rebase: merge preserves branch context; rebase rewrites commits for linear history. Use merge for shared history; use rebase locally before publishing to reduce noise.

Section 03

Remote Repositories

Manage remote endpoints, fetch updates, and push local changes safely.

Note

Set upstream tracking with git push -u or git branch --set-upstream-to to enable simpler pulls.

git remote

List and manage remote repositories.

  • -v: show URLs.
  • add <name> <url>: add remote.
  • set-url: change remote URL.
  • rename: rename remote.
  • remove/rm: delete remote.
# Add upstream remote
git remote add upstream https://github.com/org/app.git

# Change origin to SSH
git remote set-url origin git@github.com:org/app.git

# List remotes with URLs
git remote -v

git fetch

Download refs and objects from remotes without altering working tree.

  • --all: fetch all remotes.
  • --prune: remove stale remote-tracking refs.
  • <remote> <refspec>: fetch specific branches/tags.
# Update all remotes and prune stale branches
git fetch --all --prune

# Fetch only main branch from origin
git fetch origin main

git pull

Fetch then merge (or rebase) into current branch.

  • --rebase: rebase instead of merge.
  • --ff-only: refuse non fast-forward updates.
  • --all: pull from all remotes (rare).
# Rebase current branch onto upstream main
git pull --rebase origin main

# Safe pull that fails on divergence
git pull --ff-only origin main

git push

Upload local commits to a remote branch or tag.

  • -u/--set-upstream: set upstream tracking.
  • --force-with-lease: force push safely (checks remote tip).
  • --tags: push all tags.
  • <remote> :<branch>: delete remote branch by pushing nothing.
# First push and set upstream
git push -u origin feature/login

# Safe force after rebase
git push --force-with-lease origin feature/login

# Delete remote branch
git push origin :old-branch

Section 04

Tagging

Mark important points (releases) with lightweight or annotated tags.

Tip

Use annotated tags for releases: they store message, tagger, and date, and can be signed.

git tag

Create, list, or delete tags.

  • git tag: list tags.
  • -a <tag> -m "msg": create annotated tag.
  • -s: GPG-sign annotated tag.
  • -d <tag>: delete local tag.
  • -f: move tag to another commit (use carefully).
# List tags sorted by version
git tag --list --sort=v:refname

# Create annotated release tag
git tag -a v1.4.0 -m "Release 1.4.0"

# Move tag to new commit (rewrite)
git tag -f v1.4.0 HEAD

git show (tags)

Display tag metadata and referenced commit.

  • git show <tag>: show tag info and commit diff.
  • --stat: summary of changes.
# Inspect annotated tag contents
git show v1.4.0

# Summary only
git show --stat v1.4.0

Push Tags

Share tags with remotes. Tags are not pushed automatically unless specified.

  • git push <remote> <tag>: push single tag.
  • git push --tags: push all tags.
  • git push <remote> :refs/tags/<tag>: delete remote tag.
# Push a single tag
git push origin v1.4.0

# Push all tags (release day)
git push --tags

# Delete remote tag
git push origin :refs/tags/v1.3.0

Section 05

Stashing & Undoing

Temporarily shelve work, roll back changes, or revert commits safely.

Safety

Prefer revert for published commits; use reset only on local branches or when collaborators agree.

git stash

Save a snapshot of unstaged/staged changes for later.

  • push: store changes (default action).
  • -m "msg": describe the stash.
  • -u/--include-untracked: include untracked files.
  • -a/--all: include ignored files.
  • list: list stashes.
# Stash tracked and untracked files
git stash push -u -m "WIP: login form"

# List stashes
git stash list

git stash pop

Apply latest (or specific) stash and remove it from the stash list.

  • git stash pop: apply most recent.
  • git stash pop stash@{n}: apply specific entry.
  • git stash apply: apply without dropping.
# Apply latest stash and drop
git stash pop

# Apply specific stash without dropping
git stash apply stash@{2}

git reset

Move HEAD and optionally the index/working tree. Use with care.

  • --soft: move HEAD only (keep index and working tree).
  • --mixed: move HEAD and reset index (default), keep working tree.
  • --hard: reset HEAD, index, and working tree (destructive).
# Undo last commit but keep changes staged
git reset --soft HEAD~1

# Drop work completely (dangerous)
git reset --hard origin/main

git revert

Create a new commit that undoes the changes of a previous commit. Safe for shared branches.

  • git revert <commit>: revert a single commit.
  • --no-commit: stage the revert without committing.
  • -n/--no-commit: collect multiple reverts into one commit.
# Revert a bad commit on shared branch
git revert abc1234

# Revert multiple commits then commit once
git revert -n HEAD~3..HEAD~1
git commit -m "Revert problematic migrations"

Discard file changes

Restore a file to index or HEAD state. Modern alternative: git restore.

  • git checkout -- file: reset file to index/HEAD.
  • git restore file: clearer equivalent (if available).
  • git restore --staged file: unstage while keeping working copy.
# Discard local modifications (cannot undo)
git checkout -- config.yml

# Unstage but keep edits
git restore --staged src/app.js

Section 06

Diff & Log

Inspect changes and history with focused filters and readable formats.

Hint

Use --stat for summaries, --patch for details, and --color for clarity when piping to pagers.

git diff

Show changes between commits, index, and working tree.

  • git diff: working tree vs index.
  • git diff --cached: index vs HEAD.
  • git diff HEAD~1 HEAD: between commits.
  • --stat: summary of changes.
  • --word-diff: highlight word-level changes.
# View staged diff
git diff --cached

# Word-level diff for a file
git diff --word-diff src/app.py

git log (formats)

Customize history output for quick scans or audits.

  • --pretty=format:"...": custom fields (%h, %ad, %an, %s).
  • --stat: per-commit file summaries.
  • --reverse: oldest first.
  • --first-parent: follow mainline through merges.
# Custom one-line with date
git log --pretty=format:"%h %ad %an %s" --date=short -n 10

# Follow mainline only (useful on release branches)
git log --first-parent --oneline

git shortlog

Summarize commits grouped by author. Helpful for release notes or contribution stats.

  • -s: summary (counts only).
  • -n: sort by number of commits.
  • -e: include email addresses.
  • --since/--until: time-bounded summaries.
# Contributions in last month
git shortlog -sn --since="1 month ago"

# Include emails for release notes
git shortlog -se v1.3.0..HEAD

Section 07

Merge Conflicts

Detect, inspect, and resolve conflicts methodically.

Workflow

Resolve conflicts in working tree, stage resolved files, then continue (merge --continue / rebase --continue).

Detect & inspect

Use status and diff to see conflicted paths and markers.

  • git status: shows paths with conflicts (both modified).
  • git diff: shows conflict markers <<<<<<<, =======, >>>>>>>.
  • git diff --name-only --diff-filter=U: list conflicted files.
# List conflicted files
git diff --name-only --diff-filter=U

# View conflict markers in a file
git diff -- config/routes.rb

git mergetool

Launch configured merge tool to resolve conflicts visually.

  • git mergetool: open tool for each conflicted file.
  • --tool <name>: choose specific tool (meld, kdiff3, vimdiff).
  • --gui: prefer GUI tools when available.
# Use vimdiff to resolve conflicts
git mergetool --tool=vimdiff

# After resolving, stage and continue
 git add path/to/file
 git merge --continue  # or: git rebase --continue

Conflict resolution workflow

# 1) Start merge/rebase and hit conflicts
# 2) Inspect conflicts
git status

# 3) Open files, resolve markers <<<<<<< ======= >>>>>>>
# 4) Optionally use a mergetool
#    git mergetool --tool=meld

# 5) Stage resolved files
git add app/models/user.rb

# 6) Continue
# For merge:
git merge --continue
# For rebase:
git rebase --continue

# 7) If stuck, abort
# git merge --abort
# git rebase --abort

Section 08

Workflows & Best Practices

Pick a branching strategy, write clear commits, and collaborate predictably.

Commit style

Use imperative mood, keep to ~50 char subject, and wrap body at ~72 chars with rationale and context.

Branching Strategies

  • Feature branches: short-lived branches off main; rebase before merge; prefer fast-forward or squash merges.
  • Pull request flow: branch per change, open PR early, run CI, rebase/merge after review.
  • Gitflow: main + develop; release/hotfix branches; heavier but structured for releases.
  • Trunk-based: tiny, frequent merges to main with feature flags; favors CI/CD.

Commit Message Examples

feat(auth): add OAuth token refresh
fix(payments): handle declined cards gracefully
chore(ci): bump actions/cache to v4
refactor(api): simplify pagination helpers
docs: clarify onboarding steps
revert: revert "feat(auth): add OAuth token refresh"

Best Practices

  • Commit early and often; keep commits focused and reversible.
  • Prefer rebase + fast-forward for small, local cleanup; merge for shared branches to preserve context.
  • Keep main always deployable; gate risky work behind flags.
  • Protect branches: require reviews, CI, and status checks before merging.
  • Use .gitignore to keep noise out; avoid committing secrets.
  • Document decisions in commit bodies, not just PR descriptions.

Section 09

Tagging & Releases

Plan releases with semantic versioning and consistent tagging practices.

Semantic Versioning

Format: MAJOR.MINOR.PATCH (e.g., 2.3.1). Bump MAJOR for breaking changes, MINOR for new features, PATCH for fixes.

# Create release branch and tag
git switch -c release/1.4.0
# run tests, update changelog

# Tag with changelog summary
git tag -a v1.4.0 -m "Release 1.4.0 - payments and UX"

# Push branch and tags
git push origin release/1.4.0
git push origin v1.4.0

# Hotfix flow
# branch from main
git switch -c hotfix/1.4.1
# after fix:
git tag -a v1.4.1 -m "Hotfix: fix webhook retries"
git push origin hotfix/1.4.1 v1.4.1

Prefer annotated, signed tags for releases. Keep CHANGELOG.md aligned with tags; automate changelog generation from conventional commits or release notes when possible.

Section 10

Advanced Commands

Diagnose history, isolate changes, and recover from mistakes.

Caution

Commands like rebase -i, cherry-pick, and reset rewrite history. Coordinate with teammates before altering shared branches.

git cherry-pick

Apply specific commits onto current branch.

  • -x: append "cherry picked from" reference to message.
  • -n/--no-commit: apply changes without committing.
  • --continue / --abort / --skip: handle conflicts.
# Bring fix from main to release branch
git cherry-pick -x abc1234

# Apply multiple commits without auto-committing
git cherry-pick -n abc1234 def5678
git commit -m "Backport fixes"

git rebase -i

Interactively reorder, squash, or edit commits.

  • pick: keep commit as-is.
  • reword: edit commit message.
  • squash/fixup: combine commits.
  • edit: pause to amend content.
# Clean up last 5 commits
git rebase -i HEAD~5
# choose pick/reword/squash in editor
# fix conflicts if any, then continue
git rebase --continue

git bisect

Binary search commits to find where a bug was introduced.

  • start: begin session.
  • good <rev>: mark known good commit.
  • bad <rev>: mark known bad commit.
  • run <cmd>: automate tests per step.
# Manual bisect session
git bisect start
git bisect bad HEAD
git bisect good v1.3.0
# test... then mark good/bad until found

git bisect reset  # return to original HEAD

# Automated bisect with script
git bisect start
git bisect bad
git bisect good v1.3.0
git bisect run npm test
git bisect reset

git reflog

View reference logs for HEAD and branches to recover lost commits.

  • git reflog: list recent HEAD movements.
  • git reflog show <ref>: specific branch/tag.
  • git reset --hard HEAD@{n}: restore to prior position (dangerous).
# Recover after accidental reset
git reflog
# pick the wanted entry, e.g., HEAD@{3}
git reset --hard HEAD@{3}

# Inspect remote tracking ref log
git reflog show origin/main
