Section 01

Introduction / Fundamentals

Why Composition API: better logic reuse, co-located concerns, better TS inference, tree-shakeable imports.

Guideline

Prefer Composition API for complex components, reusable logic, and TypeScript-heavy projects. Options API remains fine for small/simple views.

ref() vs reactive()

import { ref, reactive } from 'vue'

const count = ref(0)              // primitive or single value
const user = reactive({           // nested object stays reactive via proxy
  name: 'Ada',
  skills: ['Vue', 'TS'],
})

count.value++                     // must use .value on refs
user.skills.push('DX')            // deep mutations stay tracked
  • Use ref for primitives or single values; access via .value in script.
  • Use reactive for cohesive objects/collections needing deep tracking.
  • Mutate reactive objects directly; avoid replacing the reference unless intended.
  • When to use: pick ref for scalar UI flags/inputs; pick reactive for grouped state you mutate in place.

toRefs(), toRaw(), markRaw()

import { reactive, toRefs, toRaw, markRaw } from 'vue'

const state = reactive({ ready: false, payload: null })
const { ready, payload } = toRefs(state) // preserves reactivity when destructuring

const raw = toRaw(state)                // escape proxy (e.g., pass to non-reactive lib)
const thirdParty = markRaw(new Map())   // opt-out of tracking for heavy structures
  • Use toRefs when exposing reactive properties to keep reactivity.
  • Use toRaw sparingly for debugging or third-party interop.
  • markRaw opts objects out of tracking (great for heavy/immutable data).
  • When to use: toRefs for consuming reactive pieces elsewhere; toRaw/markRaw only for interop or perf-critical structures.

shallowReactive / shallowRef

import { shallowReactive, shallowRef } from 'vue'

const card = shallowReactive({
  meta: { views: 0 },   // nested meta is NOT reactive
  title: 'Guide',
})

const el = shallowRef(null)       // DOM refs benefit: avoids deep tracking overhead
  • Shallow variants track only top-level properties.
  • Use when nested objects are managed elsewhere (e.g., Chart.js).
  • Helps avoid expensive deep proxying on large payloads.
  • When to use: bridges to third-party instances or large immutable blobs.

readonly() & customRef()

import { ref, readonly, customRef } from 'vue'

const internal = ref(0)
const exposed = readonly(internal)   // prevent external mutation

const debounced = (delay = 200) => customRef((track, trigger) => {
  let timer, value = ''
  return {
    get() {
      track()                   // track access
      return value
    },
    set(v) {
      clearTimeout(timer)
      timer = setTimeout(() => {
        value = v
        trigger()              // notify after debounce
      }, delay)
    },
  }
})
  • Expose readonly state to prevent external mutation.
  • customRef lets you control tracking/triggering (e.g., debounce).
  • Great for throttled flags, debounced inputs, or lazy values.
  • When to use: export read-only state to consumers; wrap inputs that need debounce/throttle semantics.

Computed Basics & Getters/Setters

import { ref, computed } from 'vue'

const first = ref('Ada')
const last = ref('Lovelace')

const fullName = computed(() => `${first.value} ${last.value}`)

const normalized = computed({
  get: () => fullName.value.toUpperCase(),
  set: (value) => {
    const [f, ...rest] = value.split(' ')
    first.value = f
    last.value = rest.join(' ')
  },
})

normalized.value = 'GRACE HOPPER'  // also updates first/last
  • Computed values are cached until dependencies change.
  • Getter/setter pairs enable two-way derived state (formatted inputs).
  • Prefer computed over watch when deriving state.
  • When to use: any time you derive view data from source state instead of imperatively syncing.

Section 02

Template Bindings

Compose bindings using refs/computed, dynamic attributes, and slot-driven layouts.

Pitfall

Remember to unwrap refs in templates automatically. In script, access .value. In templates, no .value needed.

v-model with Composition API

<template>
  <input v-model.trim="title" class="input" />
  <p>{{ title }}</p>
</template>

<script setup>
import { ref } from 'vue'
const title = ref('Hello')         // template unwraps .value
</script>

<template>
  <input v-model.number="age" type="number" placeholder="Age" />
  <input v-model.lazy="email" type="email" placeholder="Email (updates on blur)" />
  <p>{{ age }} — {{ email }}</p>
</template>

<script setup>
import { ref } from 'vue'
const age = ref(0)
const email = ref('')
</script>
  • Use modifiers (trim, number, lazy) on the consumer side; number coerces strings, lazy updates on blur/change.
  • For multiple bindings, use modelValue plus named props (v-model:title).
  • When to use: simplest two-way binding for native inputs and small forms.

Component v-model Support

<template>
  <input :value="modelValue" @input="$emit('update:modelValue', $event.target.value)" />
</template>

<script setup>
const props = defineProps({ modelValue: String })
const emit = defineEmits(['update:modelValue'])
</script>
  • Declare update:modelValue emits for each bound prop.
  • Parent controls modifiers (trim/number/lazy) on usage.
  • Keep component inputs controlled by props, emit changes upward.
  • When to use: building custom input components that need v-model support.

Named v-model (multiple bindings)

<!-- Parent -->
<template>
  <Dialog v-model:open="isOpen" v-model:title="title" />
</template>

<!-- Dialog.vue -->
<template>
  <section v-if="open">
    <header>
      <input :value="title" @input="$emit('update:title', $event.target.value)" />
      <button @click="$emit('update:open', false)">Close</button>
    </header>
    <slot />
  </section>
</template>

<script setup>
const props = defineProps({ open: Boolean, title: String })
const emit = defineEmits(['update:open', 'update:title'])
</script>
  • Each named model needs a prop and matching update:<name> emit.
  • Lets parents bind multiple independent values (e.g., open boolean + title string) without collisions.
  • When to use: components managing multiple controlled fields.

Dynamic Attributes & Classes

<template>
  <button :class="['btn', sizeClass, { 'is-loading': loading }]">
    {{ label }}
  </button>
  <div v-bind="baseAttrs" :data-role="role"></div>
</template>

<script setup>
import { computed } from 'vue'

const props = defineProps({ size: String, loading: Boolean, label: String })
const role = 'dialog'

const sizeClass = computed(() => props.size === 'lg' ? 'btn-lg' : 'btn-sm')
const baseAttrs = { id: 'panel', class: 'rounded border p-4' }
</script>
  • v-bind on objects merges attributes (great for forwarding attrs).
  • Class/style accept arrays, objects, or strings.
  • Computed classes help map props to utility classes cleanly.
  • When to use: forwarding arbitrary attributes/ARIA or mapping props to utility classes.

Conditional & List Rendering

<template>
  <div v-if="loading">Loading...</div>
  <div v-else-if="error">{{ error }}</div>
  <div v-else>
    <article v-for="post in posts" :key="post.id" class="card">
      <h4>{{ post.title }}</h4>
      <p v-show="post.excerpt">{{ post.excerpt }}</p>
    </article>
  </div>
</template>

<script setup>
import { ref } from 'vue'
const loading = ref(true)
const error = ref('')
const posts = ref([])
</script>
  • Use v-show for toggling visibility without unmounting.
  • Prefer stable keys (IDs over indexes) for v-for.
  • Use key to preserve component state across reorders.
  • When to use: branch UI states (loading/error/success) and list rendering with stable identity.

Slots

<template>
  <Card>
    <template #title>
      <h3>Custom Title</h3>
    </template>
    <p>Body goes here</p>
  </Card>
</template>

<!-- Card.vue -->
<template>
  <header class="font-semibold"><slot name="title" /></header>
  <section><slot /></section>
</template>
  • Slots let parents supply structure while children keep logic isolated.
  • Name slots (#title) for multiple regions; default slot for main content.
  • Provide sensible defaults inside the slot to avoid empty UI.
  • When to use: reusable layout shells where parents own content.

Dynamic Events

<template>
  <button v-on="listeners">Submit</button>
</template>

<script setup>
const listeners = {
  click: () => console.log('clicked'),
  mouseenter: () => console.log('hover'),
}
</script>
  • v-on object syntax binds multiple handlers at once.
  • Use computed objects for dynamic events (e.g., feature flags).
  • Great for forwarding listeners into child components.
  • When to use: listener forwarding or conditional event binding.

v-once / v-memo

<template>
  <h1 v-once>{{ expensiveTitle }}</h1>      <!-- render once, no updates -->

  <section
    v-memo="[user.id, isEditing]"           
    class="card"
  >
    <p>{{ user.name }}</p>
    <button @click="$emit('edit', user.id)">Edit</button>
  </section>
</template>

<script setup>
const props = defineProps({ user: Object, isEditing: Boolean, expensiveTitle: String })
const emit = defineEmits(['edit'])
</script>
  • Use v-once for static fragments that never update.
  • v-memo re-renders only when listed dependencies change.
  • Handy to limit reactivity in large lists or expensive subtrees.
  • When to use: static hero sections or memoizing expensive child renders.

Section 03

Reactivity Utilities

Control tracking, watchers, and scopes for predictable updates.

Edge Case

watchEffect runs immediately and tracks on access. Avoid async race conditions by cancelling or checking stale flags.

watch() vs watchEffect()

import { ref, watch, watchEffect } from 'vue'

const userId = ref(1)
const user = ref(null)
const loading = ref(false)

watch(userId, async (id, prevId, onCleanup) => {
  loading.value = true
  const controller = new AbortController()
  onCleanup(() => controller.abort()) // cancel stale fetch
  const res = await fetch(`/api/users/${id}`, { signal: controller.signal })
  user.value = await res.json()
  loading.value = false
})

watchEffect(() => {
  console.log('User changed', user.value)
})
  • watch is lazy, takes explicit sources, and exposes new/old values.
  • watchEffect runs immediately and tracks dependencies on access.
  • Use watch when you need previous values or to skip first run; watchEffect for quick derived effects.
  • When to use: watch for controlled side effects with history; watchEffect for quick reactive wiring/logging.

Deep Watching & flush

import { reactive, watch } from 'vue'

const filters = reactive({ range: { min: 0, max: 100 }, tags: [] })

watch(() => filters, (val) => {
  console.log('filters changed', val)
}, { deep: true, flush: 'post' }) // run after DOM updates
  • Use deep when observing nested objects or arrays.
  • flush: post runs after DOM updates—useful for measurements.
  • Avoid flush: sync unless absolutely needed for low-latency reactions.
  • When to use: track nested filter/state objects or DOM-dependent effects.

effectScope() & triggerRef()

import { effectScope, ref, watchEffect, triggerRef } from 'vue'

const scope = effectScope()

const stop = scope.run(() => {
  const draft = ref({ title: 'Draft' })

  watchEffect(() => {
    console.log('draft title', draft.value.title)
  })

  return () => draft                 // expose for external updates
})

const draft = stop()                 // returns ref

draft.value = { title: 'Published' } // replace object
triggerRef(draft)                    // force re-run when ref holds object
scope.stop()                         // dispose watchers
  • effectScope groups effects so you can dispose them together (great in composables).
  • Return cleanup functions to let consumers stop internal watchers.
  • triggerRef forces updates when a ref holds a non-reactive object that was replaced.
  • When to use: composables that spin up watchers you need to stop as a unit.

pauseTracking / enableTracking

import { ref, computed, pauseTracking, enableTracking } from 'vue'

const secret = ref('hidden')

const label = computed(() => {
  pauseTracking()               // ignore this read from deps
  const masked = secret.value   // not tracked
  enableTracking()
  return masked ? '***' : 'none'
})
  • Use pauseTracking to skip dependency collection for specific reads.
  • Re-enable with enableTracking once the non-reactive read is done.
  • Useful for logging or masking values without creating update chains.
  • When to use: rare cases where a read should not make the effect rerun (metrics, masked labels).

Section 04

Lifecycle Hooks

Hooks are imported functions; call them in setup().

Pattern

Encapsulate hook usage inside composables (e.g., useResizeObserver) to keep components lean.

Render & Update Hooks

import { onBeforeMount, onMounted, onBeforeUpdate, onUpdated } from 'vue'

onBeforeMount(() => console.log('about to mount'))
onMounted(() => console.log('mounted'))

onBeforeUpdate(() => console.log('before patch'))
onUpdated(() => console.log('patched'))
  • Use onMounted for DOM access, subscriptions, or initial fetches.
  • Keep onUpdated light to avoid jank; prefer watch for heavy work.
  • Pair before/after hooks to bracket setup/teardown logic.
  • When to use: DOM measurements, subscriptions, or first-load fetches that need the element tree.

Unmount & Error

import { onBeforeUnmount, onUnmounted, onErrorCaptured } from 'vue'

onBeforeUnmount(() => stopInterval())
onUnmounted(() => console.log('cleanup complete'))

onErrorCaptured((err, instance, info) => {
  console.error('child error', err, info)
  return false // returning false lets error bubble
})
  • Clean up timers/listeners in onBeforeUnmount/onUnmounted.
  • Use onErrorCaptured as an error boundary around risky children.
  • Return false to let errors bubble to global handlers/loggers.
  • When to use: wrapping third-party widgets or async children that might throw.

Activation, Render Tracking

import { onActivated, onDeactivated, onRenderTracked, onRenderTriggered } from 'vue'

onActivated(() => console.log('kept-alive activated'))
onDeactivated(() => console.log('kept-alive cached'))

onRenderTracked((event) => {
  console.log('tracked', event)
})

onRenderTriggered((event) => {
  console.log('triggered', event)
})
  • onActivated/onDeactivated fire for keep-alive cached components.
  • onRenderTracked shows which dependencies were tracked.
  • onRenderTriggered shows which dependency triggered the render.
  • When to use: profiling render causes or handling keep-alive lifecycle.

Common Mistakes

  • Using async directly in setup() without error handling.
  • Accessing DOM before onMounted.
  • Forgetting to clean up timers or listeners in onUnmounted.

Section 05

DOM References

Template refs provide typed access to elements or components.

Safety

Access refs after onMounted or await nextTick. Guard for null when conditionally rendering elements.

Template Refs

<template>
  <input ref="inputEl" class="input" />
  <button @click="focusInput">Focus</button>
</template>

<script setup>
import { ref, onMounted, nextTick } from 'vue'

const inputEl = ref(null)           // HTMLInputElement | null

const focusInput = async () => {
  await nextTick()                  // ensure DOM paint
  inputEl.value?.focus()
}

onMounted(focusInput)
</script>
  • Access DOM refs after onMounted or nextTick.
  • Guard optional chaining (?.) for conditionally rendered elements.
  • Encapsulate DOM usage in helpers like focusInput for reuse.
  • When to use: focusing inputs, measuring elements, or imperative DOM actions.

shallowRef for DOM-heavy Objects

import { shallowRef, onMounted, onUnmounted } from 'vue'

const chart = shallowRef(null)

onMounted(() => {
  chart.value = new Chart(/* ... */) // third-party instance
})

onUnmounted(() => {
  chart.value?.destroy()
  chart.value = null
})
  • Use shallowRef for third-party instances to avoid deep tracking.
  • Replace/destroy instances in onUnmounted to prevent leaks.
  • Combine with markRaw when passing instances through provide/inject.
  • When to use: wrapping chart/map/editor instances that manage their own internals.

Section 06

Events

Handle native and custom events with Composition API ergonomics.

Reminder

Use @keyup.enter, @click.prevent, and other modifiers to express intent without manual stopPropagation.

Native Events & Modifiers

<template>
  <form @submit.prevent="submit">
    <input @keyup.enter="submit" />
    <button @click.stop="log('clicked')">Save</button>
    <button @click.once="log('first time only')">Run Once</button>
  </form>
</template>

<script setup>
const log = (msg) => console.log(msg)
const submit = () => console.log('submitted')
</script>
  • Use @submit.prevent to stop form navigation.
  • .stop keeps events from bubbling; .once auto-removes after first fire.
  • Key modifiers like .enter reduce manual keyCode checks.
  • When to use: declarative event handling without manual preventDefault/stopPropagation.

Custom Events & v-on Object

<template>
  <Modal v-on="listeners" />
</template>

<script setup>
import { computed } from 'vue'

const emit = defineEmits(['close'])
const listeners = computed(() => ({
  close: () => emit('close'),
  'update:open': (val) => console.log('open', val),
}))
</script>

<!-- Child emitting custom events -->
<template>
  <button @click="$emit('save', payload)">Save</button>
</template>

<script setup>
const emit = defineEmits(['save'])
const payload = { id: 1 }
</script>
  • v-on object syntax batches handlers for forwarding listeners.
  • Declare emits for better TS inference and devtools hints.
  • Use update:modelValue to support v-model on custom components.
  • When to use: composing modals/dialogs where listeners are passed through.

Key & Mouse Modifier Examples

<template>
  <input @keyup.enter="save" @keyup.esc="reset" placeholder="Press Enter to save" />

  <button @click.prevent="submit">Submit (prevent default)
  </button>

  <button @click.ctrl.enter="submit">
    Submit (Ctrl+Enter)
  </button>

  <div class="box" @click.self="close">
    <!-- clicks on children won't close -->
    <p>Click background to close</p>
  </div>
</template>

<script setup>
const save = () => console.log('saved')
const reset = () => console.log('reset')
const submit = () => console.log('submit')
const close = () => console.log('close')
</script>
  • Combine key modifiers (e.g., .ctrl.enter) for shortcut combos.
  • Use .self to restrict clicks to the element, ignoring children.
  • .prevent stops default behavior like form submit or link nav.
  • When to use: keyboard shortcuts, backdrop clicks, or preventing default link/form behavior.

Section 07

Forms & Validation

Use refs for primitives, reactive for grouped form state, and composables for validation.

Tip

Prefer controlled inputs with v-model. For large dynamic forms, store field metadata in arrays and render via v-for.

Basic Form State

<template>
  <form @submit.prevent="submit">
    <input v-model.trim="form.email" type="email" />
    <input v-model.number="form.age" type="number" />
    <label>
      <input v-model="form.newsletter" type="checkbox" /> Subscribe
    </label>
    <button type="submit">Send</button>
    <button type="button" @click="reset">Reset</button>
  </form>
</template>

<script setup>
import { reactive } from 'vue'

const initial = { email: '', age: 0, newsletter: false }
const form = reactive({ ...initial })

const submit = () => console.log(form)
const reset = () => Object.assign(form, initial)
</script>
  • Use reactive for grouped form state; refs for primitives.
  • Object.assign resets reactive objects without breaking binding.
  • Prefer .trim/.number modifiers to coerce and clean input.
  • When to use: small-to-medium forms with simple validation needs.

Dynamic Forms & Validation

<template>
  <div v-for="field in fields" :key="field.name" class="space-y-2">
    <label :for="field.name">{{ field.label }}</label>
    <input
      :id="field.name"
      v-model="form[field.name]"
      :type="field.type"
      :placeholder="field.placeholder"
    />
    <p v-if="errors[field.name]" class="text-red-500 text-xs">{{ errors[field.name] }}</p>
  </div>
</template>

<script setup>
import { reactive, computed } from 'vue'

const fields = [
  { name: 'email', label: 'Email', type: 'email', placeholder: 'you@example.com' },
  { name: 'password', label: 'Password', type: 'password', placeholder: '••••••' },
]

const form = reactive({ email: '', password: '' })

const errors = computed(() => ({
  email: !form.email.includes('@') ? 'Email is invalid' : '',
  password: form.password.length < 8 ? 'Min 8 chars' : '',
}))
</script>
  • Computed validations stay reactive to field changes.
  • Store field metadata in arrays to render dynamic forms.
  • Debounce async validation with customRef or watch + timeout.
  • When to use: dynamic schemas or forms built from metadata.

Radios, Checkboxes, Select

<template>
  <fieldset class="space-y-2">
    <legend>Theme</legend>
    <label v-for="option in themes" :key="option" class="flex gap-2 items-center">
      <input type="radio" name="theme" :value="option" v-model="theme" />
      {{ option }}
    </label>
  </fieldset>

  <fieldset class="space-y-2">
    <legend>Stacks (multi-select)</legend>
    <label v-for="stack in stacks" :key="stack" class="flex gap-2 items-center">
      <input type="checkbox" :value="stack" v-model="selectedStacks" />
      {{ stack }}
    </label>
  </fieldset>

  <select v-model="country" class="input mt-3">
    <option disabled value="">Pick a country</option>
    <option v-for="c in countries" :key="c.code" :value="c.code">{{ c.label }}</option>
  </select>
</template>

<script setup>
import { ref } from 'vue'

const themes = ['light', 'dark']
const stacks = ['Vue', 'React', 'Svelte']
const countries = [
  { code: 'US', label: 'United States' },
  { code: 'CA', label: 'Canada' },
]

const theme = ref('light')
const selectedStacks = ref(['Vue'])
const country = ref('')
</script>
  • Radios bind a single primitive value.
  • Checkboxes with arrays accumulate selected values.
  • Select v-model binds the option value; use true-value/false-value for non-boolean checkboxes.
  • When to use: user preference pickers, multi-select filters, or country/state dropdowns.

Section 08

Error Handling

Handle async failures close to the source; provide fallbacks in UI.

Rule

Never throw from template expressions. Catch in setup and expose safe state.

try/catch in setup()

import { ref, onMounted } from 'vue'

const data = ref(null)
const error = ref('')

onMounted(async () => {
  try {
    const res = await fetch('/api/data')
    if (!res.ok) throw new Error('Request failed')
    data.value = await res.json()
  } catch (err) {
    error.value = err.message
  }
})
  • Handle async errors in setup/onMounted and expose friendly state.
  • Guard .ok before parsing; set fallback UI for error/loading.
  • Keep error strings serializable for SSR and logging.
  • When to use: component-level fetches where you control loading/error UI.

Global & Async Patterns

import { onErrorCaptured, provide, inject } from 'vue'

// Error boundary component
onErrorCaptured((err) => {
  console.error('boundary caught', err)
  return false
})

// Provide/inject error bus
const ERROR_KEY = Symbol('error')
provide(ERROR_KEY, (err) => console.error(err))

const emitError = inject(ERROR_KEY)
emitError?.(new Error('oops'))
  • Wrap risky children (charts, portals) with error boundaries.
  • Provide/inject an error bus for global logging or toast emitters.
  • Return false in onErrorCaptured to rethrow to global handlers.
  • When to use: shared logging/toast pipelines or isolating unstable child components.

Section 09

Components & Composables

Compose props, emits, slots, and reusable functions.

Pattern

Use composables for logic, components for rendering. Keep composables pure (no DOM) when possible.

Props, Emits, Slots

<template>
  <section>
    <header><slot name="title" /></header>
    <slot />
    <button @click="emit('submit')">Submit</button>
  </section>
</template>

<script setup>
const props = defineProps({
  variant: { type: String, default: 'solid' },
  modelValue: Boolean,
})
const emit = defineEmits(['submit', 'update:modelValue'])
</script>
  • Keep props serializable; avoid passing functions unless needed.
  • Emit updates instead of mutating props directly.
  • Expose named slots for flexible layout control.
  • When to use: reusable UI components that need controlled props/events.

defineAsyncComponent

import { defineAsyncComponent } from 'vue'

const AsyncChart = defineAsyncComponent({
  loader: () => import('./Chart.vue'),
  loadingComponent: () => 'Loading...',
  errorComponent: () => 'Failed to load',
  timeout: 8000,
})
  • Async components code-split heavy children to trim bundles.
  • Provide loading/error fallbacks to keep UX responsive.
  • Set a timeout so failed loads do not hang indefinitely.
  • When to use: heavy/rarely-viewed components (charts, editors, admin panels).

Composable Example

// useFetch.js
import { ref, watchEffect } from 'vue'

export function useFetch(url, options = {}) {
  const data = ref(null)
  const error = ref('')
  const loading = ref(false)

  watchEffect(async (onCleanup) => {
    loading.value = true
    const controller = new AbortController()
    onCleanup(() => controller.abort())
    try {
      const res = await fetch(url, { ...options, signal: controller.signal })
      if (!res.ok) throw new Error('Request failed')
      data.value = await res.json()
    } catch (err) {
      if (err.name !== 'AbortError') error.value = err.message
    } finally {
      loading.value = false
    }
  })

  return { data, error, loading }
}
  • Composables return refs/computed—not components or DOM.
  • Accept params for flexibility; avoid hidden singletons unless intentional.
  • Support cancellation (AbortController) for fetch-like composables.
  • When to use: shared logic across components (fetching, feature flags, keyboard shortcuts).

Provide / Inject

import { provide, inject } from 'vue'

const USER_KEY = Symbol('user')

// provider
provide(USER_KEY, { name: 'Ada' })

// consumer
const user = inject(USER_KEY, { name: 'Guest' })
  • Use symbols as keys to avoid collisions.
  • Provide/inject follows the parent chain; nearest provider wins.
  • Great for themes, i18n, and shared singletons like auth stores.
  • When to use: cross-tree data like themes, localization, or user/session context.

Section 10

Type-safe Composition API

Use TypeScript for safer refs, props, emits, and composables.

Pitfall

Always annotate generic refs (`ref(0)`). Avoid implicit any for emits payloads.

Typing refs & reactive

import { ref, reactive } from 'vue'

const count = ref(0)
const user = reactive<{ name: string; age?: number }>({ name: 'Ada' })
  • Annotate ref generics for primitives/unions.
  • Use reactive for structured objects; ref for scalars.
  • Prefer readonly/computed when exposing derived state.
  • When to use: TS-heavy components needing strict value types.

Typed props / emits

<script setup lang="ts">
const props = defineProps<{
  modelValue: string
  size?: 'sm' | 'md' | 'lg'
}>()

const emit = defineEmits<{
  (e: 'update:modelValue', value: string): void
  (e: 'submit'): void
}>()
</script>
  • Type props/emits to get template inference and editor hints.
  • Narrow strings with unions; overload emits to document payloads.
  • Use withDefaults for optional props that need defaults.
  • When to use: reusable components where payload shapes must be explicit.

Generics for Composables

// usePromise.ts
import { ref } from 'vue'

export function usePromise(fn: () => Promise) {
  const data = ref(null)
  const error = ref('')

  const run = async () => {
    try {
      data.value = await fn()
    } catch (err) {
      error.value = err instanceof Error ? err.message : String(err)
    }
  }

  return { data, error, run }
}
  • Expose typed composable APIs so callers get inference.
  • Prefer discriminated unions for status over many booleans.
  • Type async functions to surface expected payloads/errors.
  • When to use: shared composables that other teams consume.

Section 11

Advanced Reactivity Patterns

Optimize tracking and understand proxy caveats.

Gotcha

Destructuring reactive objects breaks reactivity unless wrapped with toRefs.

watch vs watchEffect

// watch: specify sources, get old/new
watch(() => route.query.page, (page, prev) => {
  console.log('page changed', page, prev)
})

// watchEffect: good for derived side effects
watchEffect(() => {
  document.title = `Users | page ${route.query.page}`
})
  • Use watch when you need old values or to skip the initial run.
  • watchEffect is great for quick reactive side effects without boilerplate.
  • Prefer computed when deriving state instead of watch.
  • When to use: watch for controlled side effects; watchEffect for quick wiring; computed for pure derivations.

Proxy Caveats

import { reactive } from 'vue'

const state = reactive(new Map())
state.set('id', 1)          // reactive
const raw = Array.from(state.entries()) // snapshot, non-reactive array
  • Some collection methods return raw values (e.g., spreading a Map).
  • Wrap derived snapshots in computed to stay reactive.
  • Avoid mutating raw snapshots—mutate the reactive source.
  • When to use: handling Maps/Sets where spreading breaks reactivity.

Handling Large Objects Efficiently

import { shallowReactive, markRaw, computed } from 'vue'

const cache = shallowReactive({})
const large = markRaw({ huge: true }) // opt-out of tracking
cache.snapshot = large

const entries = computed(() => Object.keys(cache))
  • Use shallowReactive or markRaw for heavy objects or caches.
  • Normalize data before storing to reduce deep watcher churn.
  • Expose computed snapshots instead of raw objects when possible.
  • When to use: large payloads, caches, or normalized store data.

flush option in watch()

watch(() => props.modelValue, () => {
  // read DOM after it updates
}, { flush: 'post' })
  • Use flush: post when effects depend on rendered DOM.
  • flush: sync is rare—reserve for ultra-low-latency needs.
  • Default flush: pre suits most data-side effects.
  • When to use: DOM measurement after render, or ultra-low-latency reactions.

Vue Router Patterns

import { useRoute, useRouter, onBeforeRouteUpdate } from 'vue-router'

const route = useRoute()

Section 13

Best Practices / Performance

Keep components focused; avoid unnecessary reactive work.

Checklist

  • Prefer computed over watch when deriving state.
  • Dispose listeners/timers in onUnmounted.
  • Code-split large routes with async components.

Organizing setup()

// good: top-level imports, composables first, events last
import { useFetch } from '@/composables/useFetch'

const { data, loading } = useFetch('/api')
const onClick = () => {/* ... */}

// avoid: deeply nested logic in setup; move to composables
  • Order setup: imports, state, computed, watchers, then handlers.
  • Extract branches/loops into composables to keep setup lean.
  • Group related logic together to improve readability.
  • When to use: any component with growing setup complexity.

Minimizing Re-renders

import { computed } from 'vue'

const expensiveList = computed(() => items.value.slice(0, 10)) // limit work
  • Split components to shrink reactive scope.
  • Memoize derived data with computed instead of recalculating.
  • Paginate or window large lists to avoid heavy renders.
  • When to use: performance-sensitive views with large lists or expensive child renders.

SSR / Hydration

// avoid direct window/document in setup during SSR
let width = 0
if (typeof window !== 'undefined') {
  width = window.innerWidth
}
  • Guard browser-only APIs for SSR (check typeof window).
  • Keep initial state deterministic to avoid hydration mismatch.
  • Use onMounted for client-only work after hydration.
  • When to use: universal apps rendered on both server and client.

Mixing Options & Composition

  • You can mix Options + Composition, but prefer one style per file.
  • Use setup within Options components when migrating gradually.
  • Document patterns so teams stay consistent.
  • When to use: incremental migrations from Options API or legacy components.

Mini App Example

<template>
  <section class="space-y-4">
    <input v-model="term" placeholder="Search users" class="input" />
    <ul>
      <li v-for="user in filtered" :key="user.id" class="flex items-center gap-2">
        <span class="font-semibold">{{ user.name }}</span>
        <button @click="select(user)">Select</button>
      </li>
    </ul>
    <p v-if="selected">Selected: {{ selected.name }}</p>
  </section>
</template>

<script setup>
import { ref, computed } from 'vue'

const term = ref('')
const users = ref([
  { id: 1, name: 'Ada' },
  { id: 2, name: 'Grace' },
])

const filtered = computed(() =>
  users.value.filter((u) => u.name.toLowerCase().includes(term.value.toLowerCase()))
)

const selected = ref(null)
const select = (user) => (selected.value = user)
</script>
  • Combines refs, computed filtering, and event handlers.
  • Demonstrates key rendering with v-for + :key.
  • Extend with async fetch via useFetch to load users.
  • When to use: starting point for list + filter + selection patterns.
