Section 01

Fundamentals

Relational databases store data in tables (relations) made of rows (records) and columns (attributes).

Tip

Always specify column lists on INSERT/SELECT to avoid coupling to schema order.

Data Types Snapshot

Numeric

INT, BIGINT, DECIMAL(p,s), FLOAT

Character

CHAR(n), VARCHAR(n), TEXT

Temporal

DATE, TIME, TIMESTAMP, INTERVAL

Boolean & Misc

BOOLEAN, UUID, JSON, ARRAY

Basic Query Anatomy

SELECT column_list
FROM   table_name
WHERE  condition
ORDER  BY column ASC
LIMIT  10 OFFSET 0;

Clauses run conceptually in the order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.

Example

SELECT id, first_name, last_name, email
FROM   customers
WHERE  country = 'US'
   AND created_at >= DATE '2025-01-01';

Section 02

Filtering & Sorting

Fine-tune result sets with comparison operators, boolean logic, and pagination helpers.

Warning

Always pair LIMIT with ORDER BY for deterministic paging.

WHERE Logic

SELECT *
FROM   orders
WHERE  status IN ('pending','processing')
   AND total >= 100
   AND NOT (country = 'CA' AND expedited = false);

Comparison Operators

= : equality != / <> : not equal >, >=, <, <= : numeric compare BETWEEN, LIKE, ILIKE

Ordering & Pagination

SELECT id, shipped_at, total
FROM   orders
WHERE  shipped_at IS NOT NULL
ORDER  BY shipped_at DESC, id ASC
LIMIT  20 OFFSET 40; -- page 3 (0-index)

Use keyset pagination for large datasets:
`WHERE (shipped_at < :cursor_date) OR (shipped_at = :cursor_date AND id < :cursor_id)`.

Section 03

Aggregations

Aggregate functions crunch rows into summarized insights.

Note

Every non-aggregated column in SELECT must appear in GROUP BY in standard SQL.

SELECT  customer_id,
        COUNT(*)          AS order_count,
        SUM(total)        AS revenue,
        AVG(total)        AS avg_value,
        MIN(created_at)   AS first_order,
        MAX(created_at)   AS last_order
FROM    orders
GROUP   BY customer_id
HAVING  SUM(total) >= 5000
ORDER   BY revenue DESC;

`HAVING` filters aggregated rows. Use window functions when you need aggregates alongside detail rows.

Section 04

Joins

Combine tables via matching keys to reveal relationships.

Reminder

Qualify column names (table.column) to avoid ambiguity and to help query planners use indexes.

Join Matrix

INNER JOIN: matching rows only.
LEFT JOIN: all left rows, nulls for missing right.
RIGHT JOIN: mirror of LEFT.
FULL OUTER: all rows from both.
CROSS JOIN: Cartesian product.
SELF JOIN: join same table with aliases.

Example

SELECT o.id,
       o.total,
       c.company_name,
       s.name AS salesperson
FROM   orders AS o
JOIN   customers AS c   ON c.id = o.customer_id
LEFT JOIN sales_reps AS s ON s.id = o.sales_rep_id
WHERE  o.created_at >= CURRENT_DATE - INTERVAL '30 days';

Section 05

Subqueries

Nest queries inside others to reuse logic or filter using derived sets.

Guideline

Use CTEs for readability when subqueries become complex or reused multiple times.

Scalar & Table Subqueries

SELECT id,
       total,
       (SELECT AVG(total) FROM orders) AS avg_all
FROM   orders
WHERE  total > (
  SELECT AVG(total)
  FROM   orders
  WHERE  customer_id = orders.customer_id
);

SELECT *
FROM   (
  SELECT customer_id, SUM(total) AS revenue
  FROM   orders
  GROUP  BY customer_id
) AS stats
WHERE  revenue > 10000;

Correlated Subquery

SELECT c.id, c.company_name
FROM   customers AS c
WHERE  EXISTS (
  SELECT 1
  FROM   orders AS o
  WHERE  o.customer_id = c.id
     AND o.total >= 1000
);

SELECT o.*
FROM   orders AS o
WHERE  total = (
  SELECT MAX(total)
  FROM   orders
  WHERE  customer_id = o.customer_id
);

Section 06

Set Operations

Combine results vertically. Ensure column counts and types align.

-- UNION: distinct rows across queries
SELECT email FROM newsletter
UNION
SELECT email FROM customers;

-- UNION ALL: keep duplicates
SELECT email FROM newsletter
UNION ALL
SELECT email FROM customers;

-- INTERSECT: common rows
SELECT product_id FROM inventory
INTERSECT
SELECT product_id FROM promotions;

-- EXCEPT / MINUS: rows in first not second
SELECT id FROM customers
EXCEPT
SELECT customer_id FROM blacklist;

Some engines use `MINUS` (Oracle) instead of `EXCEPT`. Wrap complex subqueries with parentheses when mixing operations.

Section 07

Modifying Data

Change data using DML statements with guardrails.

Safety

Never run UPDATE/DELETE without a WHERE clause unless that's intentional. Use transactions + backups.

INSERT

INSERT INTO products (name, price, in_stock)
VALUES ('Widget Mini', 49.00, true);

INSERT INTO products (name, price)
VALUES ('Widget Pro', 199.00),
       ('Widget Ultra', 299.00);

UPDATE

UPDATE products
SET    price = price * 0.9,
       updated_at = NOW()
WHERE  category = 'Clearance';

Use RETURNING (Postgres) to fetch affected rows.

DELETE

DELETE FROM sessions
WHERE  last_seen < NOW() - INTERVAL '30 days';

Prefer archival tables for compliance before removal.

Section 08

Table Management

Define schema structure, indexes, and constraints carefully.

Create & Alter

CREATE TABLE customers (
  id           SERIAL PRIMARY KEY,
  company_name VARCHAR(120) NOT NULL,
  email        VARCHAR(255) UNIQUE,
  country      CHAR(2) NOT NULL,
  created_at   TIMESTAMP DEFAULT NOW(),
  CHECK (country = UPPER(country))
);

ALTER TABLE customers
ADD COLUMN phone VARCHAR(32);

DROP TABLE IF EXISTS temp_import;

Indexes

CREATE INDEX idx_orders_customer_created
ON orders (customer_id, created_at DESC);

DROP INDEX idx_orders_customer_created;

Foreign Keys

ALTER TABLE orders
ADD CONSTRAINT fk_orders_customer
FOREIGN KEY (customer_id)
REFERENCES customers(id)
ON DELETE CASCADE;

Section 09

Transactions

Group statements into atomic units to maintain integrity.

Isolation

Choose isolation level (`READ COMMITTED`, `SERIALIZABLE`, etc.) based on concurrency requirements.

BEGIN;
  UPDATE accounts SET balance = balance - 500 WHERE id = 1;
  UPDATE accounts SET balance = balance + 500 WHERE id = 2;
  SAVEPOINT after_transfer;
  DELETE FROM pending_transfers WHERE id = 99;
  -- if something fails later
  ROLLBACK TO after_transfer;
COMMIT; -- or ROLLBACK;

Use `SET TRANSACTION ISOLATION LEVEL` inside transactions to override defaults.

Section 10

Views & Stored Procedures

Encapsulate complex logic and reuse in clients.

Views

CREATE OR REPLACE VIEW v_customer_revenue AS
SELECT  c.id,
        c.company_name,
        SUM(o.total) AS total_revenue,
        COUNT(o.id)  AS orders
FROM    customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
GROUP   BY c.id, c.company_name;

SELECT * FROM v_customer_revenue WHERE total_revenue > 10000;

Stored Procedure (PostgreSQL)

CREATE OR REPLACE FUNCTION award_loyalty(p_customer INTEGER)
RETURNS VOID AS $$
BEGIN
  INSERT INTO loyalty_points (customer_id, points)
  VALUES (p_customer, 100)
  ON CONFLICT (customer_id)
  DO UPDATE SET points = loyalty_points.points + 100;
END;
$$ LANGUAGE plpgsql;

SELECT award_loyalty(42);

Parameters & Result Sets

Procedures/functions support IN / OUT params, cursors, and transaction control. Syntax varies by RDBMS (MySQL `DELIMITER`, SQL Server `CREATE PROCEDURE`).

Section 11

Advanced Features

Modern SQL engines include analytical functions, JSON helpers, triggers, and diagnostic tools.

Window Functions

SELECT order_id,
       customer_id,
       total,
       ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at) AS order_rank,
       SUM(total) OVER (PARTITION BY customer_id ORDER BY created_at ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total
FROM   orders;

CTEs

WITH monthly AS (
  SELECT DATE_TRUNC('month', created_at) AS month,
         SUM(total) AS revenue
  FROM   orders
  GROUP  BY 1
)
SELECT month,
       revenue,
       LAG(revenue) OVER (ORDER BY month) AS prev_month
FROM   monthly;

Triggers

CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at := NOW();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_products_updated
BEFORE UPDATE ON products
FOR EACH ROW EXECUTE FUNCTION set_updated_at();

JSON / Array Helpers (Postgres)

SELECT data - 'deprecatedKey' AS cleaned
FROM   products_json;

SELECT jsonb_extract_path_text(meta, 'dimensions','width')
FROM   inventory_json;

SELECT tags && ARRAY['featured'] AS is_featured
FROM   articles;

Performance

  • Use `EXPLAIN (ANALYZE, BUFFERS)` to inspect query plans.
  • Create covering indexes for high-frequency filters.
  • Avoid functions on indexed columns (`WHERE LOWER(email)` prevents index usage).

Section 12

Best Practices

Consistency and clarity keep SQL maintainable.

  • Alias wisely: use short, descriptive table aliases and column aliases for derived values.
  • Avoid SELECT *: list needed columns for performance and clarity.
  • Index strategically: monitor slow queries, add composite indexes for filter + sort columns.
  • NULL handling: prefer `COALESCE`, `IS NULL`, `IS NOT NULL` to avoid surprises.
  • Transactions: wrap multi-step changes, handle errors with rollbacks.

Formatting

Uppercase SQL keywords, indent joins/conditions, and align ON clauses for scan-friendly queries.

Monitoring

Track slow query logs, add query timeouts, and measure cardinality estimates after schema changes.
